### 1. The Release Reviewer's new routing closed a security gap without waking anyone

On ATL-93 it rejected, and the rejection is worth reading in full on the Task.
`renderTodo` interpolated the todo id into `<li data-id="${t.id}">` with no
escaping — the only value on the row that skipped the module's own `escape()`.

The Architect's spec had already ruled this out of scope as "pre-existing and
unchanged". The Release Reviewer overruled it:

> Pre-existing is true; unchanged is not. On `origin/main`, `renderPage` is
> imported at `src/server.js:4` and never called […] ATL-95 adds `GET /todos` →
> `renderPage(...)`, which is precisely what turns a dormant string-building bug
> into a live, unauthenticated, user-facing surface.

It reproduced it with two payloads rather than inferring it, filed **ATL-107**
(`dev`, `fullstack`) itself, and the build step picked it up because it was the
only open sub-task. Fixed, tested (`test/atl-107.test.js`), re-verified through
every gate, PR opened. **No Owner involvement.** Under v2 this parked.

This is also the case for the Release Reviewer existing at all: no per-sub-task
reviewer could have seen it, because the danger comes from one sub-task adding a
route that makes another sub-task's existing code reachable.


`frontend-only` is the fixture where the visual gate is supposed to have real
work. The detection was an extension list —
`tsx|jsx|vue|svelte|css|scss|less|html` — and the sandbox is a server-rendered

file is a UI change whatever the file is called. Verified against both real
branches — ATL-93 triggers it (81 markup lines), ATL-94's cache work does not.
